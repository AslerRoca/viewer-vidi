## P12 — Films without a header window: default window from the VOI LUT, uniform re-export, rectangle masks, list marks  ·  2026-11-25
- **Anchor:** `bbac2d7` (branch `wip/report-viewer`; code uncommitted at entry time — P10–P12 land together in the WIP commit that follows this entry)

**Assumption.** After P11 the user reported that "the W/L of the AGFA films is also not the same as the others". First suspicion: a side effect of the MONOCHROME1 flip (window not mirrored). Wrong — the films concerned have no window to mirror, and the picture was the same before the flip (old viewer: percentile window on the stored values + Invert = new viewer: percentile window on the flipped values, within ±1 grey level).

**What we did.** *Diagnosis, on a finished hand-crop job (≈620 saved films from four makers; headers of all, pixels of all; aggregate numbers only).* Header survey by maker: three makers carry `WindowCenter` / `WindowWidth` (one value each; for the DX "FOR PRESENTATION" films it is simply the full 12-bit range, the image is already display-ready). The fourth — CR films, MONOCHROME1, `RescaleType = LOG_E REL`, about one film in six — has **no window at all** and instead one `VOILUTSequence` item per film (`LUTExplanation` RP1KT or NK5; ≈760–1,730 entries, first mapped stored value ≈1,260–2,370; output runs 0–4095 although the descriptor says 16 bits; `LUTData` arrives as raw bytes (VR OW) in some files and as a list in others — decode bytes as `<u2`). The viewer never read lookup tables: `wl_from_dicom` returned nothing and the loader fell back to `wl_from_percentiles` — centre = median, width = p98 − p2 **of the whole plate**. Measured consequence: the crop (upper chest) is only ≈7 % of the plate on these films, so the guess sits on the plate around the patient (centre ≈980 in flipped values) while the anatomy sits around ≈1,610, above the window's upper edge. Under that default the median crop was 92 % pure white (IQR 16–96 %); in ≈70 % of the films more than half of the crop was saturated white, in ≈5 % (plate mostly unexposed, the guess lands on the other side) more than half black. Accordingly ≈94 % of these films had been windowed by hand before saving, against ≈2 % of the films with a header window; the hand-set widths (recovered by regressing the saved PNG on the values) ranged from 0.26× to 2.4× the LUT's range. The saved 8-bit crops of that maker therefore carried operator-dependent contrast; NIfTI was unaffected.
*The table itself.* It is one fixed curve, shifted and stretched per film: at 25 / 50 / 75 % of its input range the output is 0.077 / 0.354 / 0.721 (a straight line would give 0.25 / 0.5 / 0.75), i.e. in brightness terms it rises faster than the line and saturates — brighter mid-tones. Candidate rules, compared in the crop against the maker's own rendering (LUT applied, MONOCHROME1 inverted): viewer guess — mean |difference| 66 grey levels; straight window over the LUT's input range — 41 (mean grey 141 vs 184, SD 25 vs 30: darker and flatter, but nothing saturated); whole-film p0.5–p99.5 (what the downstream training loader does) — 24 but unstable (IQR 8.5–78: it depends on how much of the plate is background); percentiles of the crop itself — the only rule that gives comparable contrast across all makers (SD 44–51).
*Options put to the user.* A: default window = input range of the VOI LUT (small change, W/L drag as before). B: apply the curve for display and 8-bit export (exact maker picture; touches the CPU + GPU render path, W/L semantics and the export). The user chose **A**.
*Implemented.* `windowing._voi_lut_range` + `wl_from_dicom`: header window, else the LUT's range (`LUTDescriptor`: entries — 0 means 65,536 — and first mapped value), mirrored for MONOCHROME1; the percentile guess stays as third fallback. Manifest columns `wc`, `ww`, `wl_default` (1 = the film's default window, 0 = set by hand), so the two can be told apart afterwards — until now the window of a save was recorded nowhere. `tools/update_exports.py` for output directories written before: `--default-window` renders the PNG / JPEG image and crop of films without a header window again with the default window, Invert off (replaced files are first moved to `<output dir>/replaced-<time>/`; rows get `wc`, `ww`, `wl_default = 1`, `invert = 0`; NIfTI untouched; films with their own header window untouched); `--rect-masks` see below; dry run by default, second run finds nothing to do, slices of volumes are left alone. It re-uses `export_item`, `apply_rescale`, `wl_from_dicom` and the panel's orientation flips, so it writes exactly what a Save would.
*Rectangle as a mask.* Asked whether "the mask" had been saved: it had not — nothing was ever painted in that job, only rectangles, and **Mask** meant the painted area only, so ticking it wrote nothing. That expectation had surfaced twice (P11's "ticked Mask later, still no mask"). Now, with **Mask** ticked and a rectangle, `export_item` also writes `<stem>_rect_mask`: uint8 on the whole image, 1 inside the rectangle, same geometry as `<stem>_image`. `update_exports.py --rect-masks` adds it to every saved row with a rectangle (pixel spacing taken from the row's existing NIfTI image).
*List marks (made in a parallel session on the same working tree, taken over here).* Each list row shows its running number; `⚠` marks an item saved with neither a rectangle nor a mask (`workspace.row_is_empty`, `Item.empty`), with a tooltip, and the counter under the list names how many.
*Dead ends.* (a) My first rendering of the maker's picture scaled the LUT output by 2¹⁶ − 1 (the descriptor's bit count) and came out almost white; the table's real maximum is 4095. (b) A quick "is this saved crop a negative?" test — closer to the default rendering or to its inverse — mislabelled a few hand-windowed crops; the correlation with the film's values (as in `repair_mono1.py`) found none. (c) I guessed the stable plate median was a constant fill outside the collimation; the most frequent single value covers < 2 % of the plate, so it is a noisy background, not a fill.

**What we got.** Tests: `test_annot.py` 72/72 (default window of a film without header window; rectangle mask with and without a painted mask and only with Mask ticked; `wc` / `ww` / `wl_default` for a default and a hand-set window), `test_mono1.py` 22/22 (LUT-range window incl. mirroring, 0 = 65,536 entries, header window wins; `update_exports.py` dry run / apply / second run on an old-style output directory, replaced files kept byte-identical in the backup folder, repair tool undisturbed by the new files), `test_list_marks.py` 13/13, `test_fixes.py` 44/44, `tests/reports/test_reports.py` 71/71. Applied to the real job on the user's word: the ≈420 PNG / JPEG image and crop files of the films without header window were rendered again — every one identical to today's default rendering; crop mean grey 141 [135–146], SD 25 [22–27], pure white 0 % in the median crop (worst film 6 %), pure black 0 %; JPEG vs PNG mean difference 1.4 grey levels. ≈1,870 rectangle-mask files written (three formats per row); all checked: mask size = image size, mask = rectangle, NIfTI geometry = the image's, every file named in the manifest exists, every pre-existing manifest column except `files` unchanged. For comparison, the makers' own header windows differ too (crop mean grey ≈158 and ≈94 for the two large groups), so 8-bit crops are not comparable across makers whatever the viewer does.

**Try next.** For any cross-maker analysis read the NIfTI crops and normalise per crop; do not rely on the 8-bit windows. Option B (apply the curve) only if A's flatter picture is not enough. Decide whether the few films *with* a header window that were saved with a hand-set window should be re-rendered with their default too. Still open from P11: the NIfTI repair on the old exports. Check on the real display.

## P11 — MONOCHROME1 films flipped at load; Invert reset, right-click tool menu, deleted items not saved, masks kept and restored  ·  2026-11-25
- **Anchor:** `bbac2d7` (branch `wip/report-viewer`; code uncommitted at entry time)

**Assumption.** Four requests collected on 2026-11-18 while a crop round was running (done only after it, on the user's word): Invert should go back to off after a save; the tools should be reachable at the cursor by right-click; an item marked as deleted must not be saved again by Save & Next; and a mask ticked later should be writable because "the mask should exist already somewhere". A fifth came from use on 2026-11-24: the films of one CR maker are stored as `MONOCHROME1` (high value = black) and the viewer ignored that flag (open item #75 since P6), so they showed as negatives until Invert was pressed. Assumed consequence, confirmed in the code: PNG / JPEG follow the screen (right only if Invert was on at the save), NIfTI holds the stored values whatever Invert says (always a negative for these films), and the manifest recorded neither polarity nor Invert.

**What we did.** *Polarity.* `windowing.mono1_flip_sum(ds)`: for MONOCHROME1 the constant S with which `S − v` turns a rescaled value into its MONOCHROME2 counterpart, `S = slope · (lo + hi) + 2 · intercept` with `lo + hi` from the header alone (`BitsStored`, `PixelRepresentation`: 2^bits − 1 unsigned, −1 signed) — 4095 − v for an unsigned 12-bit film. From the header and not from the image's own min / max on purpose: every film gets the same flip, and a crop can be flipped without its full image. `apply_rescale` applies it, `wl_from_dicom` mirrors a header window (`centre → S − centre`, width kept); all DICOM reads already pass through these two functions (2 + 3 call sites), so display, hover value, W/L, ROI statistics, time curves and every export agree: high = white. Decided by `PhotometricInterpretation` alone; `PresentationLUTShape` stays out until a film needs it. `SeriesData.photometric`; manifest columns `photometric` and `invert`; the info overlay reads `MONOCHROME1 (shown flipped: high = white)`. Invert stays a display / 8-bit-export switch on top.
*Old exports.* `tools/repair_mono1.py <output dir>`: for every saved row with an empty `photometric` it reads only the header of the source; for MONOCHROME1 it rewrites the NIfTI image and crop as `S − v` (atomically, header and affine kept, `descrip = "vidi: MONOCHROME1 flipped"` so a file is never flipped twice even if a run dies before the row is marked), leaves masks alone, fills `photometric`; other films only get the column filled. PNG / JPEG are never changed, only checked: correlation of the product with the film's stored values in the same region — r > 0.2 = negative (saved without Invert), r < −0.2 = right, else unclear. Dry run by default.
*Invert.* `AnnotationDock.item_saved` → the toolbar button is unchecked after every successful Save / Save & Next, which un-inverts the saved panel; the files keep the inversion they were saved with.
*Right-click.* `ImageCanvas.context_requested(QPoint)` is emitted for a right-click the canvas has no use for (not after a right-button drag, which pans; not in the time-curve modes; not while a polygon has vertices, where it removes the last one). The dock answers with a menu of the tool row — W/L, Brush, Polygon, Rect (current one ticked) and Erase — only while it is visible. Undo / Clear deliberately left out (Ctrl+Z exists; a destructive entry next to tool choices invites misclicks).
*Deleted.* `_save` returns early for an item marked as deleted: Save says so, Save & Next only moves on. The previous behaviour ("saving a deleted item restores it") is gone; plain Save is refused the same way.
*Masks.* Reproduced first on the fixtures: a mask painted and saved with Mask unticked is written when Mask is ticked and the item is still on screen, but after Next / Prev the canvas is empty (annotations are reset with the image), and saving then wrote the original only, **deleted the earlier crop as stale and emptied the rectangle columns of the row** — a second save could destroy the first. Now every successful save keeps the painted mask in `<output dir>/work/<stem>_mask.png` whatever is ticked (`write_work_mask`; an empty mask removes the copy), and `ViewCell.load_finished` → `AnnotationDock._restore_annotation` puts mask and rectangle (manifest `x0…y1`) back via `ImageCanvas.set_annotations` (no undo step) when the item is reopened. Guards: only the panel that loaded the item, only a row with status saved, only on the view recorded in the row (`view` column — for a volume that means the slice shown right after loading), and never over fresh drawing. Items saved before work copies existed fall back to a mask product named in the row (PNG, else NIfTI). Marking an item deleted removes the kept mask with the products.

**What we got.** Tests at this point: `test_annot.py` 68/68 (13 new: flipped NIfTI and `photometric` on a real MONOCHROME1 fixture; Save and Save & Next on a deleted item; mask kept with Mask unticked, restored with its rectangle, written after ticking Mask, fallback to the mask product, removed on delete; Invert saved, recorded and off afterwards; the menu opens, lists the tools with the current one ticked, switches the tool and Erase; no menu after a right-drag, during a polygon, or with the dock closed), `test_mono1.py` 13/13 (flip constant for unsigned / signed / rescaled; window mirrored; a fixture loads as 4095 − stored and its MONOCHROME2 twin — tag changed, pixels flipped — loads to the identical array; repair on an old-style output directory: dry run writes nothing, apply rewrites exactly the NIfTI image and crop of the MONOCHROME1 films and the manifest, repaired values equal what the viewer now loads, unknown columns kept, second run changes nothing, a file already rewritten is not flipped again), `test_fixes.py` 44/44, `test_reports.py` 71/71. The repo's four test fixtures turned out to be MONOCHROME1 films themselves, which made the flip testable without new data. Dry run of the repair on the finished crop job: about one film in six is MONOCHROME1; two NIfTI files per film would be rewritten; **all** of their PNG / JPEG products are the right way round (Invert had been on every time).

**Try next.** Run the repair with `--apply` on the old exports — rewrites data files, so only on the user's explicit word (a run attempted on a bare "continue" was stopped by the session's safety check; nothing was changed). Until then rows with an empty `photometric` follow the old convention and whatever reads those NIfTI files must flip them itself. Possible additions nobody asked for: Undo / Clear in the menu; restoring an annotation on a volume slice other than the first one shown.

## P10 — Workspace dock: list dropped on "Open list…", crop rectangle adjustable by edges and corners, enlarge button per panel  ·  2026-11-18
- **Anchor:** `bbac2d7` (branch `wip/report-viewer`; code uncommitted at entry time)

**Assumption.** Two requests from the first days of real use: a list file should be openable by dragging it from the study list onto the dock's **Open list…** button, and the crop rectangle should be correctable by its edges and corners instead of being redrawn each time. Both looked like additions to existing paths: the private drag mime type of P9 already carries the dragged paths, and the canvas already stores the rectangle in image coordinates with an undo stack.

**What we did.** *List drop.* `_ListDropButton(QPushButton)` accepts a drag only if it carries exactly one path (`drag_state.decode_paths`) with a list extension (`workspace.LIST_EXTS`); folders, images, several items and drags from other applications are refused at `dragEnterEvent`, so nothing opens halfway. `dropEvent` emits `list_dropped(str)`, connected **queued** to `_open_list_file` (split out of `_open_list`): a list without images is answered with a dialog, and a modal dialog must not open while the drop is still being delivered. No `dragMoveEvent` is needed — Qt pre-accepts moves once the enter was accepted.
*Rectangle.* `ImageCanvas._rect_hit(pos)` returns which edge(s) lie within `_GRAB_PX = 6` screen pixels of the cursor (−1 / +1 per axis, both set on a corner); `_rect_cursor` shows the matching resize cursor; a press on an edge stores `(x edge, y edge, press position, rectangle at the press)` and `_drag_rect_edges` moves the grabbed edge(s) by the distance dragged, clamped to the image and to at least one pixel of rectangle, pushing **one** undo step per adjustment (at the first actual change, so a mere click changes nothing). A drag started anywhere else draws a new rectangle as before. Eight 7×7 handles are drawn only while the Rect tool is active. Edges move by whole screen pixels — about 2 image pixels per step on a full chest film at normal size; zoom first for pixel-exact edges.
*Enlarging a panel.* The user asked why a double-click did not enlarge the panel. Reproduced: it does with the W/L tool or with the dock closed, and by design (since P5) not while Brush, Polygon or Rect is selected — Polygon closes its outline with the double-click, Brush and Rect swallow it so that quick clicks cannot flip the layout. Rather than change that rule, on the user's suggestion every panel got a **⤢** button at the right end of its header (`ViewCell._max_btn`, checkable, `Qt.NoFocus` so the canvas keeps the keyboard) that emits the existing `double_clicked` signal; `QuadView` reports the state back with `set_enlarged`, so button and double-click never disagree.
*Testing detours.* `QTest.mouseDClick` sends only the double-click event, no preceding press — a real double-click is `mouseClick` + `mouseDClick`. The `offscreen` platform stubs drags entirely; `minimal` runs the real drag loop but sends no DragLeave after a refused drag, so Qt keeps the stale drop target and later drags silently do nothing — the end-to-end script has to send `QDragLeaveEvent` itself (xcb does this on its own). A `.dcm` file in a folder not yet classified as DICOM is filtered out of the study list, and the proxy then returns no mime data at all — the test builds that mime by hand.

**What we got.** `test_annot.py` 42 → 57 checks, all passing: 9 for the rectangle (cursor shapes over edge / corner / inside; handles only with the Rect tool; an edge drag moves only that edge and the dock's size line follows; a corner moves two edges; one undo step per adjustment; edges stop at the opposite edge and at the image border; a click on an edge changes nothing; a drag away from the edges draws a new rectangle), 3 for the list drop (accepts one list file only; a dropped list opens in list mode and loads its first item; a list without images gives the warning and keeps the workspace), 3 for the enlarge button (enlarges while a drawing tool owns the double-click; pressed again restores; follows a double-click on another panel). The real drag loop on `minimal` with the repo fixtures: list → button opens it, list → image panel refused, folder → button refused, text file without image paths → warning after the drag has ended. Minimum panel width unchanged for normal names (worst case, a 28-character series name with the time-curve buttons, 467 → 494 px). README: one table for the three drag targets of the study list, the rectangle adjustment, the enlarge button.

**Try next.** The ⤢ glyph comes from a system font (present on the Linux machine, not checked on the Mac — draw an icon if it shows as a box). Dragging a folder onto **Open directory…** would be the natural twin of the list drop; not asked for.

## P9 — Drag a folder or file from the study list onto the Reports panel  ·  2026-11-13
- **Anchor:** `cebfda1` (branch `wip/report-viewer`; code uncommitted at entry time — P7–P9 land together in the next WIP commit)

**Assumption.** The study list already drags image series onto the image panels (`_SmartProxy.mimeData` plus the `drag_state` payload), so the Reports panel only has to accept the same drag and read the path from it. Wrong in one point, found on reading the code: `mimeData` returned `None` whenever the selection was not an image series, so a report folder or a `.txt` / `.csv` file could not be dragged at all — the drag never started.

**What we did.** `drag_state.py`: private mime type `application/x-vidi-paths` (NUL-separated UTF-8) with `encode_paths` / `decode_paths`. A private type on purpose instead of `text/uri-list`: with file URLs a drop outside the viewer would make the file manager copy the dragged folder. `tree_panel._SmartProxy.mimeData` now always returns mime data naming the dragged paths and adds the series payload + `application/x-dicom-series` only when the selection is an image series — image panels behave as before and refuse report drags. `ReportPanel`: `setAcceptDrops(True)`; `dragEnterEvent` accepts only a drag carrying exactly one path (several items, and drags from other applications, are refused rather than half-loaded); `dropEvent` calls `open_source(path)`, the same call as the Open buttons. No handlers on the child widgets: Qt offers a DragEnter to the parents until one accepts and then delivers move/drop to that widget, so drops on the list, the text or the filter field reach the panel. Hint added to the empty panel's source line; README bullet.
Performance at drag start: the tree's series probe (`_make_series_meta`) runs in the GUI thread when a drag begins. On a report folder of ≈7,600 files on the exFAT research drive it stalled ~865 ms. Short-circuiting the sub-directory test and switching to `os.scandir` brought only 794 ms; profiling showed that `os.listdir` alone costs ~390 ms there and ran twice (in `_make_series_meta` and again in `_make_grouped_meta`). The listing is now passed on (`_make_grouped_meta(study_dir, names)`): ~435 ms, i.e. one directory read.
Two testing detours. (a) The new test block segfaulted (exit 139, output lost to buffering; `python -u -X faulthandler` put it in `tree_panel.canFetchMore`): the test helper held a plain `QModelIndex` of the `QSortFilterProxyModel` across event processing, while the tree calls `invalidateFilter()` every 80 ms after background classification and thereby drops the proxy's indexes. The helper now builds proxy indexes on the spot from paths — a test bug, not an application bug. (b) An end-to-end drag did nothing on the `offscreen` platform (the drag loop returned after 0.00 s): its `QOffscreenDrag` is a stub that returns `IgnoreAction`. `QT_QPA_PLATFORM=minimal` runs the real `QSimpleDrag` loop. The end-to-end and profiling scripts lived in the session scratchpad; their results are reproduced here.

**What we got.** `tests/reports/test_reports.py` 71/71 — 7 new checks: the series probe still groups sub-series and a report folder is no series; a dragged report folder names its path and is no series; a drop on the report text opens the folder; a file dropped on the report list opens that file; several items at once and foreign drags are refused; an image panel refuses a report drag; an image folder still drags as a series. Existing suites unchanged: `test_annot.py` 42/42, `test_fixes.py` 44/44 (all three rerun at entry time). Full drag through Qt's drag loop on `minimal` with synthetic data: folder → report text opened its 40 reports, folder → report list opened its 12, folder → image panel was refused and nothing changed. Viewer started on the real display (xcb, 1400×900) with an empty Reports panel: accepts drops, right two panels hidden, panel 770 px wide. Not yet seen: the mouse gesture itself on the real display. Remaining cost: ~0.4 s of hesitation when the drag of a folder with thousands of files begins (one directory read by the drive).

**Try next.** Confirm the gesture on the real display. If the ~0.4 s at drag start bothers: take the series probe out of the drag start (reuse the tree's background classification, or probe on drop). Still open from P7/P8: even split vs. right column + 220 px, report list beside the text, a `--reports <folder>` start argument, full-text search, linking a report to the loaded study by patient ID. Commit the branch (WIP) and decide the merge of `wip/roi-export` + `wip/report-viewer` → `master`.

## P7 — Reports dock: read `.txt` / `.rtf` folders and CSV report exports beside the images  ·  2026-11-11
- **Anchor:** `cebfda1` (new branch `wip/report-viewer` off `wip/roi-export`; code uncommitted at entry time)

**Assumption.** Radiology reports can be read inside the viewer straight from the exports as they lie on disk — a folder with one text file per report, or CSV tables with one report per row and the text as RTF — with no conversion step and no database. Three things had to hold: (1) a table export of several hundred MB can be listed without loading it, by indexing the byte offset of every row and reading rows on demand; (2) a small stdlib RTF converter reproduces the text of the already existing single-file export; (3) reports written from different templates can be formatted from their layout alone (capitals, short heading lines, bullets, `key: value`), so no template is hard-coded. Decided with the user before building: own branch off `wip/roi-export`, a right-hand dock like the Workspace, standalone for now (no link between a report and the loaded images).

**What we did.** `rtf_text.py` (stdlib, no Qt): one tokenizer regex (control word + argument, `\'hh`, control symbol, braces, literal run); a group stack carrying the `\ucN` skip count and an "ignoring" flag; 18 ignored destinations (`fonttbl`, `colortbl`, `stylesheet`, `themedata`, `listtable`, …) plus every `\*` group; `\par` / `\line` / `\tab` / `\cell` mapped to text; `\uN` with its fallback characters skipped; `\'hh` bytes decoded with the code page the document declares (`\ansicpgN`, else cp1252); `clean_text` trims line ends and collapses runs of blank lines.

## P2 — Layer-by-layer input probe; bypass Qt via kernel evdev  ·  2026-07-17
- **Anchor:** `2a91e4f`

**Assumption.** Some layer between mouse and app accumulates tilt detents and flushes only on a full/second detent. Initial hypothesis: libinput's hi-res (v120) wheel handling, or the kernel `hid-logitech-hidpp` multiplier.

**What we did.** Probed every layer of the Linux input stack in isolation (all probe scripts in session scratchpad, results reproduced here):
1. **Kernel (evdev):** raw read of `/dev/input/event7` (G502 via Lightspeed receiver, `hid-logitech-hidpp`, HID++ 4.2) decoding `struct input_event`. 
2. **libinput config:** toggled `libinput High Resolution Wheel Scroll Enabled` 0/1 via `xinput` (Ubuntu 24.04, libinput 1.25.0, xf86-input-libinput 1.4.0, X11 session).
3. **Qt delivery:** probe window logging every `QWheelEvent` (`angleDelta`, `pixelDelta`, phase, source); repeated with `Qt.AA_CompressHighFrequencyEvents` disabled.
4. **X server delivery:** `xev`, watching legacy scroll buttons 6/7.

Findings: kernel emits `REL_HWHEEL ±1` + `REL_HWHEEL_HI_RES ±120` immediately for **every** single click (nothing accumulated; hold auto-repeats at ~100 ms; wheel wobble adds stray vertical ±15 hi-res events). Hi-res toggle: no effect. `xev`: X server delivers every detent 1:1 as button 6/7. Qt probe: isolated clicks **never delivered**; first event of a burst arrives as −240/−360 (2–3 detents flushed at once), proving Qt's scroll-valuator baseline goes stale during idle. Event compression off: no change. **Conclusion: Qt 5.15 xcb loses isolated horizontal scroll detents; not fixable from app-level Qt code.**

Fix: new `tilt_evdev.py` (stdlib-only) — `find_tilt_devices()` parses `/proc/bus/input/devices` for the `REL_HWHEEL` capability bit; `TiltWheelReader` reads `/dev/input/event*` on a daemon thread (select loop, 3 s hotplug rescan for receiver reconnects) and emits one Qt signal per detent (+1 right / −1 left). `MainWindow` routes it to `active_cell().step_time(steps, wrap=True)`, gated on `QApplication.activeWindow()` (evdev is global). `ViewCell.qt_tilt_suppressed` makes the Qt wheel path consume tilt events without stepping (no double-steps during holds). Without read permission (`input` group) it prints a hint and falls back to the Qt path. One-time setup: `sudo usermod -aG input $USER`.

**What we got.** User-confirmed on hardware: every single tilt click steps exactly one frame, both directions, no warm-up, direction changes instant. 12/12 headless checks pass (wrap both ways, suppression, discovery finds `event7`, fallback boot without permissions). macOS path untouched (pure Qt).

**Try next.** Soak-test in daily use, then merge `wip/wheel-tilt-scrub` → `master`. Open: single-click tilt behavior on macOS Qt (may or may not share the Qt 5.15 bug — different QPA plugin); revisit if the G502 is ever used there.
